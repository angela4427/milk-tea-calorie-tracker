# PRD：奶茶热量记录小工具（点单工作台）

- 文档类型：产品需求（PRD）/ 设计规格
- 版本：v1.0
- 日期：2026-09-09
- 状态：待产品确认后进入实现计划
- 产品形态：Web 点单工作台（必须登录）

---

## 1. 背景与目标

### 1.1 要解决的问题

减脂/健身用户把奶茶当作高频「超标项」，但现有工具要么是全品类饮食账（太重），要么只有单点热量（假精确）。用户需要按品牌、饮品、杯型、糖度、小料算出**热量区间**，记入当日额度，并能复盘本周、对比规格、复用常点单。

### 1.2 成功标准（第一版）

对用户：

- 3 分钟内完成「注册 → 登录 → 记一杯 → 看到今日区间汇总与预算进度」。
- 能看最近 7 天趋势、历史改删、收藏一键再记、同一饮品两种规格对比。
- 理解热量是参考区间，不是医疗级数值。

对作品集：

- 能讲清目标用户、非目标、热量口径、账号与数据隔离。
- 前后端边界清楚，验证码不在前端生成，历史快照不被目录更新改写。

### 1.3 非目标（第一版明确不做）

- 拍照识菜单/小票、全品类饮食、体重/运动同步、社交。
- 微信小程序、微信登录。
- 官方营养声明或单点「精确到 1 kcal」。
- 品牌 CMS 后台。
- **找回密码**（忘密码只能重新注册或由演示库重置，不在产品内提供）。
- Redis、微服务拆分。

---

## 2. 用户与使用场景

**主用户**：减脂/健身，经常喝奶茶，要控制这一项热量。

**典型场景**：

1. 点单前对比「大杯全糖珍珠」和「中杯少糖无小料」的区间差，再决定。
2. 喝完立刻按真实规格记账，看今日是否顶到奶茶预算。
3. 周末看本周哪天喝多了；常点的一杯收进收藏。

**作品集读者**（非产品用户）：校招面试官，通过 Demo 与本文判断产品完整度与工程取舍。

---

## 3. 产品原则

1. **区间优于假精确**：展示 `约 min–max kcal`，页面附参考说明。
2. **进度按上限对齐预算**：今日进度用各记录 `kcal_max` 之和对照日预算，避免「看起来没超、实际上可能已超」。
3. **快照不可变**：保存时写入当时规格与当时区间；之后改品牌库不改历史。
4. **无账号无账本**：未登录不能记账、不能看今日/历史/收藏/对比结果落库。
5. **缺配置不给选**：目录没有的组合不可选，不编造数字。

## 4. 信息架构与页面

| 页面 | 谁能进 | 作用 |
|------|--------|------|
| 注册 | 未登录 | 手机号 → 短信验证码 → 两次设置密码 |
| 登录 | 未登录 | 手机号 + 密码 |
| 今日 | 已登录 | 当日区间汇总、日预算进度、收藏快捷再记 |
| 记一杯 | 已登录 | 品牌 → 饮品 → 杯型 → 糖度 → 小料 → 预览 → 保存 |
| 对比 | 已登录 | 同一饮品最多两个规格并排，展示区间差 |
| 历史 | 已登录 | 按时间倒序，可编辑规格或删除 |
| 我的 | 已登录 | 日预算、收藏管理、退出登录 |

未登录访问需登录页的路由，一律跳转登录。

## 5. 功能需求

### 5.0 时区

所有「今日」「自然日」「每日发送上限」均按 **Asia/Shanghai** 日历日切分，不使用浏览器本地时区、不用 UTC 日期。服务端生成记录时间戳存 UTC，聚合时转到上海时区再按日切。

### 5.1 注册

顺序固定，不可跳过验码直接设密：

1. 输入中国大陆 **11 位手机号**，格式不通过则不能发码。
2. 「获取验证码」：后端先校验格式；若该手机号**已注册**，**不发送短信**，提示去登录。未注册则校验频控后调用短信通道，发送 **6 位数字码**。
3. **60 秒**内同一手机号不能重发；验证码 **5 分钟**失效。
4. 同一手机号发送上限：每小时最多 **5** 次，每个上海时区自然日最多 **10** 次；超限提示稍后重试，不发送。
5. 用户提交验证码，服务端核对且未过期后，进入设置密码。
6. 密码自定义，**再输入一次确认**，两次必须一致。
7. 密码规则：至少 **8 位**，须**同时包含字母和数字**。前端拦截 + 后端再验。
8. 密码仅存哈希（BCrypt），明文不落库、不入日志。
9. 手机号全局唯一。提交设密时若已注册，提示去登录，**不创建第二账户**。

验证码**只由后端生成并存储（含过期时间）**，前端不生成、不写死。

### 5.2 登录

- 已注册用户：手机号 + 密码。
- 日常登录**不使用**短信验证码。
- 成功后建立服务端 Session，通过 **HttpOnly Cookie**（`SameSite=Lax`）维持登录。
- 失败：统一「手机号或密码错误」，不暴露该号是否已注册（注册页的「已注册去登录」除外）。
- 退出：清除 Session，之后需重新登录。

第一版**不做**找回密码、不做第三方登录。

### 5.3 记一杯

路径：**品牌 → 饮品 → 杯型 → 糖度 → 小料（可多选）→ 预览区间 → 确认保存**。每步可返回修改。

预览展示 `约 {min}–{max} kcal` 与一句参考说明（非医疗建议）。

保存写入该用户一条记录快照，至少包括：

- 用户 ID、时间（服务端时间）
- 品牌、饮品、杯型、糖度、小料列表
- 当时的 `kcal_min`、`kcal_max`
- 目录版本号（便于审计）

保存成功后进入「今日」，能看到刚记的那条计入汇总。

### 5.4 热量区间规则

- 每个可选组合必须能从目录规则得到 `kcal_min` 与 `kcal_max`，且 `min ≤ max`，`min ≥ 0`。
- 杯型、糖度、小料会移动区间两端（大杯抬高两端；全糖靠近上限；少糖/零糖靠近下限；小料按份加在两端）。具体系数放在品牌库 JSON 中，PRD 不写死某品牌官方数字。
- 第一版品牌库：**至少 10 个品牌**，固定收录：喜茶、奈雪的茶、蜜雪冰城、霸王茶姬、茶百道、古茗、一点点、CoCo都可、书亦烧仙草、沪上阿姨。每品牌 **4～8 款**有配置的饮品；每款含杯型/糖度/小料的可选枚举与区间参数。宁缺毋假。无数据的规格不出现在选项里。
- 文案口径：整理自公开信息的**估算区间**，仅供参考。

### 5.5 今日与日预算

- 今日汇总：当日该用户所有未删除记录的 `kcal_min` 求和、`kcal_max` 求和，展示为区间。
- 用户可在「我的」设置**奶茶日预算**（正整数 kcal）。未设置时默认 **300**。
- 进度条分母为日预算，分子为今日 `kcal_max` 之和。超过预算仅提醒，**不禁止**再记。
- 「今日」提供收藏条目的一键再记（带出规格，仍需确认保存）。

### 5.6 本周趋势

- 最近 7 个自然日（含今天），按日一张柱。
- 柱高对应该日 `kcal_max` 之和；同时提供当日区间或上限的可读数字。
- 点击某天进入该日历史列表（无记录则空态）。

### 5.7 历史

- 当前用户记录按时间倒序。
- 可编辑规格：按记一杯同样规则重算区间，**更新快照为编辑当时的规格与区间**；保留原 `createdAt`，写入 `updatedAt`，列表展示最后修改时间。
- 可删除；删除后今日与趋势立即不含该条。
- 不能看到任何其他用户的记录。

### 5.8 收藏

- 收藏对象是「品牌 + 饮品 + 完整规格」，不是某条历史记录 ID。
- 同一用户同一规格不重复收藏。
- 「我的」可取消收藏。

### 5.9 对比

- 仅同一饮品；最多 **两个**规格并排。
- 展示两个区间、差值（用上限差 + 下限差同时给出），以及杯型/糖度/小料差异摘要。
- 对比页可以「把其中一套存成记录」或「收入收藏」，仍需已登录。

## 6. 系统架构

### 6.1 职责划分

| 单元 | 做什么 | 怎么用 | 依赖 |
|------|--------|--------|------|
| Web 前端 | 路由、表单、点单步骤、图表展示 | 浏览器访问 | 后端 REST、Cookie |
| 应用后端 | 注册态机、鉴权、账本 CRUD、聚合今日/周 | 前端调 API | PostgreSQL、短信网关、品牌库 |
| 品牌库 | 可选项与区间计算参数 | 后端启动加载；计算接口给前端预览或后端权威计算 | 仓库内 JSON |
| 短信网关 | 把验证码发到手机 | 后端 `SmsSender` | 云厂商；本地 Mock |

**热量权威计算在后端**：前端可预览，保存时以后端计算（或后端校验与目录一致）为准，防止改请求体写入任意热量。

### 6.2 数据流

**注册**：手机号 → 后端频控 → 生成验证码入库（过期时间）→ `SmsSender` → 用户提交验证码 → 校验 → 两次密码一致且合规 → 创建用户（手机号唯一约束）→ Session。

**记一杯**：已登录 → 选规格 → 后端按目录算区间 → 用户确认 → 插入快照 → 今日聚合读该用户当日快照。

**目录更新**：只影响新预览与新保存；已有快照字段不变。

### 6.3 会话与隔离

- Spring Security + 服务端 Session + HttpOnly Cookie（`SameSite=Lax`；`Secure` 在 HTTPS 开启，本地开发可关）。
- 所有账本 API 从 Session 取当前用户 ID，禁止客户端传「替别人记账」的 userId。
- 退出即失效 Session。

### 6.4 错误处理

| 情况 | 产品行为 |
|------|----------|
| 短信通道失败 | 明确「发送失败，请稍后重试」，不提示「已发送」 |
| 验证码错误或过期 | 可重填或重新获取（仍受 60 秒与次数上限） |
| 两次密码不一致 | 不创建账号 |
| 手机号已注册（点获取验证码或提交设密） | 不发短信 / 不创建第二账户，提示去登录 |
| 未登录调账本 API | 401，前端跳转登录 |
| 目录无该组合 | 选项不可选；若直调 API 则 400 |
| 保存失败 | 提示重试；界面不得显示成功 |
| 区间无法计算 | 不展示数字，阻断保存 |

## 7. 技术栈与选型理由

| 层 | 选型 |
|----|------|
| 前端 | Vue 3、Vite、TypeScript、Vue Router、Pinia、Tailwind CSS |
| 后端 | Java 17、Spring Boot 3、Spring Security |
| API | REST JSON |
| 数据库 | PostgreSQL |
| 品牌库 | 仓库内版本化 JSON，启动加载 |
| 短信 | `SmsSender` 接口；生产阿里云或腾讯云；本地与测试 Mock（验证码打日志/固定测试号） |
| 工程 | 单仓库前后端分目录；Docker Compose 启动 PostgreSQL 与后端 |

**理由与优势**（摘要）：

1. **秋招匹配**：Java/Spring 与 Vue 3 均为国内校招高频栈，可讲注册态机、Session、哈希与数据隔离。
2. **边界清晰**：前端负责步骤与展示，后端负责验码、鉴权、权威热量与落库。
3. **类型约束**：TS + Java 降低规格/快照字段漂移。
4. **PostgreSQL**：手机号唯一、验码后写用户可用事务；按用户隔离账本。第一版验证码带过期时间存库，不上 Redis。
5. **HttpOnly Session**：适合密码登录的 Web，降低 XSS 窃 Token；与「必须登录」一致。
6. **短信可替换**：Demo 用 Mock，避免真实短信卡住交付。
7. **Tailwind、不上大型组件库**：页面少，避免做成中台后台脸。
8. **Vite 与 Spring 分工**：改交互不必等 Java 编译；Compose 方便按 README 起 Demo。

刻意不选：Next.js 全栈（与多数 Java 岗叙事较弱）；微信小程序（已定 Web）；Redis/微服务（第一版不需要）。

## 8. 数据模型（逻辑）

- **User**：id，手机号（唯一），密码哈希，日预算（默认 300），创建时间。
- **SmsChallenge**：手机号，验证码 **BCrypt/哈希**（不存明文），过期时间，发送时间，用途=`REGISTER`，校验失败次数（超过 5 次作废该码）。
- **DrinkCatalog**：仓库内 JSON，含 `catalogVersion` 与品牌列表。每款饮品给出可选 `sizes` / `sweetness` / `toppings`；计算用基准区间 + 各选项对 min/max 的加减（kcal，整数）。后端提供纯函数：给定品牌、饮品、规格 → `{min,max}` 或「不可选」。
- **Entry**：id，userId，快照字段（品牌/饮品/规格/min/max/catalogVersion），createdAt，updatedAt。删除为**硬删**，无回收站。
- **Favorite**：userId + 规格唯一键。

验证码建议存哈希，日志只打「已发送至尾号 XXXX」，不打完整码（Mock 环境允许在服务端控制台打印以便 Demo）。

## 9. 测试要点

必须覆盖：

- 验证码：正确、错误、过期、60 秒重发、小时/日上限。
- 注册：两次密码不符、密码规则不符、重复手机号（含：已注册号点获取验证码不发短信）。
- 登录：错误密码、未注册号与错误密码同样文案；Session 退出后失效。
- 隔离：用户 A 不能读写 B 的记录与收藏。
- 快照：更新目录 JSON 后旧 Entry 的 min/max 不变。
- 聚合：今日 min/max 等于当日各条相加；预算进度用 max 之和。
- 对比：跨饮品不允许；超过两个规格不允许。
- 短信：测试默认 Mock，不调用真实网关。

## 10. 约束与合规

- 面向中国大陆手机号；短信需用户主动触发，遵守频控，避免骚扰与刷接口。
- 热量与预算均为自我管理工具，界面声明**非医疗建议**。
- Demo 预置测试账号若存在，只能走本地 Mock 码或种子数据，不得把真实短信密钥提交进 Git。
